### 拆单静默丢行（2026-09-24 修复）与 `拆单_未认领产品行.xlsx`

**症状**：`223320260001297365 / 26MT-05X246A / 26MT-05X246-YH` 我方只有 24,300、飞书 48,600。

**根因**（不是"去重"）：出运单 `PI-26MT-05X246A` 里本来就有**两条几乎一样的产品行**
——`26MT-05X246-1` 与 `26MT-05X246-2`，金额 24,300、规格、数量全同，只有 SKU / 客户货号不同；
而报关单 `223320260001297365` 只有 **1 行、总价 5,367.46**（= 一条产品行的价，报关重量 106kg）。
子集和只能闭合其中一条，**另一条既没进记录、也不报错**，于是整张采购单只算了半个成本。
（`app/services/knapsack_split.py` 的求解器只负责"给报关单找够金额"，落单后的残料无人过问。）

**修法**（`scripts/run_split_knapsack.py`）：

1. **先让它可见**：拆单全量跑完后，把「进了候选池、却没有任何报关单认领」的产品行列到
   `outputs/shipments_split/拆单_未认领产品行.xlsx`（当前 42 行 / 57,728.23 USD，其中 20 行是
   金额为 0 的行）。同一行会被多张报关单共用，所以按**内容键**去重（不能按对象 id：索引每读一次
   就重建一批 dict）。
2. **再修可判定的**：只在「同一张出运单 + 同一采购单 + 同品名 + 同金额 + 同数量、只差 SKU」的
   孪生行确实有一条被本合同的记录认领时，把另一条作为**成本补记行**并进那条记录：
   `出运金额`、`报关金额` 一点不动（报关单原件的事实），只把它的 `出运采购金额(RMB)` 加进成本，
   并在拆单明细新增的「补记成本」列写明。
3. 本轮全量只有 **1 条记录**命中（正是 05X246A），成本 24,300 → **48,600 = 飞书**，
   全量从 正常 376 / 异常 60 变成 **正常 377 / 异常 59**，没有别的记录被带动。
   ⚠ 规则**刻意写得很窄**：剩下的 22 行有金额的未认领行（06M138A、03P200Y-A&229Y-A、
   10E185B&228A、03P039Y-A、07F196B、06N121C）**没有自动处理**，等业务确认后再定。

### 「小于 1 个货币单位的补充差额」与「缺报关单」的判定（2026-09-28）

**用户口径**：业务为了把报关金额与出运金额抹平，会手工补一笔很小（≤1 个货币单位）的客户费用
（`26MT-01P242Y-C` 就是 0.01 USD）；这种零头**忽略不计**，并且允许在「报关单不齐」时照常计算。

**动了四处"要不要报关单全齐"的判断**：

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| `run_split_knapsack.py` → `directed_split_rows`：一组货 ↔ 多张报关行的金额核对 | 相对差 ≤2% | 相对差 ≤2% **或** 绝对差 ≤1 个货币单位（`IGNORABLE_DIFF_CENTS=100`） |
| 同上：单张报关行装不下一组货（>2 倍）时跳过 | 直接跳过 | 差额在 1 个货币单位以内的不算「装不下」 |

### 出运数量核验：出运数量不能比入库数量多（2026-09-28 新增）

**规则（用户口径）**：同一采购单的**出运数量 > 入库数量** = 凭空冒出来的货 → 该采购单**整组进待核实表**
（2026-09-28 最新口径：先丢待核实、后续不再处理；不再单独留在异常表）；
可以有剩余（出运 < 入库），不能反过来。对"报关单不齐也能算"的单子一并翻旧账核验，
对"报关单全齐才能匹配"的单子在原处核验；核验不通过就把该采购单的所有记录都标成 `待核实`。

**怎么算**（`scripts/build_cost_match.py` → `shipment_quantities()` / `quantity_check()`）：

| 口径 | 做法 |
| --- | --- |
| 出运数量 | 睿贝出运产品行的数量合计，**只算计数单位**（EA/PC/PCS/个/只/支/件…）；按「SKU + 数量 + 美元金额」**去重**——同一票货常被 PI 号和供应商自家 S 号各录一遍（实测 `26MT-02N105`、`26MT-05X167`、`26MT-03T094Y-HD`） |
| 入库数量 | 两路取**保守值**：① 入库单「实发区块」数量合计；② 明细行数量按单位族（count/length/weight）求和（同行同族多列只取最大值，避免重复计数） |
| 不算异常的情况 | ① 入库单某个单位族的数量与出运数量相等（±1）→ 只可能是**单位口径不同**（实测 `26MT-03P262Y`：睿贝写 EA、实际是米，米数 294 = 出运 294）；② 入库单实发区块数量已够；③ 入库单认不出数量（=0，无法核验） |

**为什么只算计数单位**：长度/重量单位的单子两边口径对不齐（入库单常用 KG、睿贝用米），
硬比会造一堆假异常。本批 1586 张有数量的采购单里，**227 张两边都是计数口径**可核验。

**命中**：**只有 1 张采购单**——`26MT-02N182-角钢`：出运 9（`PI-26MT-02N182B` 6 + `26MT-02N182I` 3）
＞ 入库 6（`26MT-02N182角钢 勇恒 入库单.xlsx`），凭空多出 3 件，出运单上这 3 件的美元金额是随手填的 0.01。
该采购单的 3 行记录（含原本判"正常"的报关单 `224420260011166466`）全部改判**待核实**，原因列 =
`出运数量 > 入库数量`，写进 **`成本匹配_待核实.xlsx`**（`待核实类型` = 出运数量 > 入库数量），
「待核实事由」里带上用到的出运单号、入库单文件名与多出来的数量；
「缺什么数据」= 需要业务/仓库确认这批货是漏货、退换货还是出运单多填（出运单上的美元金额疑似随手填的 0.01）。
