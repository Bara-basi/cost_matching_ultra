# 有效入库单提取方案（2026-09-23 待确认）

目标：从每个采购单的 N 份附件里，**去掉旧版、保留不同批次**，拿到尽可能 100% 正确的入库单。

## 一、已核实的先验

### 1. 附件列表顺序 = 上传顺序，越靠后越新 ✅

顺序取睿贝 `purchase.find` 返回的 `attachmentList` 原始次序（缓存在
`.cache/erp/attachments/lists/<采购单号>.json`）。

- 「更新 / 最终 / 补款 / 补做 / 最后一批」这类词，**出现在列表后半段的 37 例，
  夹杂出现的只有 5 例**；
- 批次字母在列表里普遍按 A→B→C→D 排列（如 `25MT-03R372Y-YH` 的 A、B、C、D）；
- 带日期的多附件单里，日期随顺序递增 3 例、违反 2 例（2 例都是麦金那批合并结算单）。

结论：**以列表顺序为「新旧」的判据**，其余线索只作辅助。

### 2. `(1)(2)` 后缀与先后无关 ✅（与你的推测不同）

(n) 后缀出现在列表后半段 19 例，出现在前半段 **36 例**。
看具体案例即可明白：`25MT-03R372Y-YH` 的顺序是 `-A(1)`、`-B`、`-C(1)`、`-D(2)`
——批次顺序完全正常，(n) 只是工厂本地转存时留下的重名后缀。
所以 **(n) 必须当噪声剥掉**，不能拿来判断新旧。

### 3. 一个采购单 = 一个单号 + 一个供应商（你的口径）✅

据此把「同一采购单下出现别的单号 / 别的供应商」一律当异常处理，清单见第四节。

### 4. 不同批次不合并 ⚠️（修正上一版文档）

上一版《入库单附件命名调研》里写的「批次 → 相加」作废。
本方案改为：**每个批次单独产出一条记录，分别核算成本**。

## 二、提取方案（决策树）

```
输入：一个采购单目录下的全部附件（按睿贝列表顺序）

Step 0 归属
   以「目录名 = 采购单」为准；附件名里的单号只做校验，不做归属依据。

Step 1 清洗
   剥掉尾部 (n)、日期戳、状态词（回传/签字/已确认/审核…），得到 [批次令牌]。

Step 2 分组（按批次令牌）
   批次令牌 = 单号核心之后的第一个短令牌，跳过供应商缩写：
       -A / -B / -C      → 批次 A/B/C
       -1 … -8           → 数字批次
       第二批 / 最后一批  → 中文批次
       -CMCS / -1AMCS    → 取「去掉供应商缩写后的部分」
   没有批次令牌的 → 归入「单一批次」
   每个批次各自独立，不合并。

Step 3 组内定版（同一批次内的多份）
   3.1 完全重复（同名，或只差 (n)）      → 去重，留一份
   3.2 费用补充件（补款/补样品费/补木箱费/含绳子费/包装费/补坡口费…）
                                        → 不与正单竞争，作为该批次的增量单独保留
   3.3 版本替换（更新/最终/最新/已修改/2.0）
                                        → 取列表顺序最靠后的一份，其余进「旧版」清单
   3.4 名字判不出（无任何信号）
                                        → 内容判定：同批次内两份的明细（规格+数量）
                                          一致或后一份是前一份的超集 → 版本替换，取后者；
                                          两份明细互不相同且互补 → 视为两批，都保留。

Step 4 校验
   4.1 组内自洽：订单数据合计 vs 实发数据合计 vs 本次付款 + 预付款
   4.2 单采购单闭合：各批次有效入库单合计 vs 该采购单金额
       （ERP 金额是「旧数据」，只当量级参考；不闭合的进人工清单）

Step 5 输出
   ① 有效入库单清单（采购单号 / 批次 / 文件名 / 列表序号 / 保留理由）
   ② 已丢弃_旧版清单（文件名 + 丢弃理由）
   ③ 人工确认清单（单号异常 / 供应商异常 / 真重复 / 内容无法判定）
```

## 六、实施（2026-09-24 已落地）

### 6.1 读取方案

「把附件读成人和模型都能看的文本，再交给规则或模型」——两层：

| 文件 | 职责 |
| --- | --- |
| `app/services/sheet_reader.py` | 附件 → 文本/图片：xlsx/xlsm 用 openpyxl、xls 用 xlrd、PDF 用 pypdf 抽文本、图片直接交给视觉；统一输出「带行号的紧凑表格文本」 |
| `app/services/deepseek_client.py` | DeepSeek 客户端（OpenAI 兼容）：JSON 模式、限速、重试、`set_min_interval()` 支持并发 |
| `app/services/grn_extract.py` | 单份附件 → 结构化：**规则优先**（迈拓模板）+ **模型兜底**（版式异常、图片、PDF、校验不自洽）；结果落缓存 |
| `app/services/grn_select.py` | 分批 + 去旧版 + 费用件单列，产出「有效入库单」 |
| `scripts/parse_grn.py` | 全量解析（`--workers` 并发、`--no-model` 只跑规则、断点续跑） |
| `scripts/select_grn.py` | 全量选择 + 导出三张表 + 与采购单金额对照 |

模型：`deepseek-chat`（实测路由到 **deepseek-flash**，1M 上下文，`input_modalities` 含 image，
可直接读 PNG/JPG）。key 取 `.env` 的 `DEEPSEEK_API_KEY`。

### 6.2 规则解析的口径（迈拓模板）

- 抬头（品名/供应商/日期）只在**表头行之前**找，避免被表头里的「品名」列名覆盖；
- 列标签 = 表头行到明细行之间所有行的纵向拼接，明细行原样保留 `{列标签: 值}`；
- **实发数据区**的金额才是结算金额（订单数据区的合计不含事后费用）；
- 明细区里没有序号的行走「费用/辅料行」（管帽、吊绳、渗透实验费…），
  计进 `extra_fees`，校验时按 `合计 = 明细求和 + 费用行` 判；
- 一张表里出现多个「实发数据-A / -B / -C」区块（一个文件覆盖多个批次）时，
  规则层主动放弃、交给模型按 `batches` 数组逐批次读。

### 6.3 缓存与断点续跑

```
.cache/erp/attachments/parsed/<采购单号>/<文件名>.json
```

按文件内容 sha256 前 16 位失效；`--no-model` 跑出来的失败结果不会被「允许用模型」的下一轮复用。

### 6.4 选择层的判定顺序（`app/services/grn_select.py`）

1. **按批次分组**：批次令牌取「单号后面紧跟的短令牌」（`-A`/`-B`、`-1`/`-8`、「第二批」、
   `-CMCS` 这类尾巴），跳过 `-YH/-HD/-XMLS` 等供应商缩写；`-1-` 这种属于单号本身的
   采购批次不算发货批次。**不同批次各自保留，不合并。**
2. **组内去重/定版**：同名（剥掉 `(n)`）或内容相同的只留最靠后一份；
   带「更新/最终/最新/已修改」的取最靠后一份；费用补充件（补款/木箱费/样品费…）与正单并列保留。
3. **跨批次的「递进快照」**：一份附件的**货物身份**（材质+品名+规格+数量，不含金额）
   是另一份的真子集 → 判早期版本、丢弃；
   身份完全相同但金额不同 → 疑似价格更正，**两份都留并标注**待人工确认。
   例：`26MT-01P242Y` 的 A（仅 A 批）/ B（A+B）/ C（A+B+C）只留 C 与 D，
   合计 751281.65 与采购单金额完全一致。
4. **同名同额的跨批次副本**：用采购单金额当参照——去掉副本后更接近采购单金额就判重复，
   否则按两批保留并标注。

## 八、模型解析复核（2026-09-24 追加）

第七节那组数字（1636 规则 / 399 模型）是**规则解析被逐列校验通过前**的中间状态，已作废。
当前口径见下表。

### 8.1 一个真 bug：喂给模型的表格文本被截断在 24 列

`sheet_reader.sheets_to_text()` 原来写死 `max_cols=24`，而财务的入库单经常是**宽表**：
一个文件横向铺开 A/B/C/D 四个批次的「数量 / 重量 / 金额」列。

| 采购单 | 附件 | 列数 | 后果 |
| --- | --- | --- | --- |
| `25MT-03P005-BF` | `25MT-03P005-BCD_宝丰_入库单_(2).xlsx` | 37 | C、D 两批在第 25~36 列，模型只读到 A、B，金额 129,334.32（实际 683,015.32） |
| `26MT-03P200Y-HX` | `-B` / `-C_沪新_入库单_回传.xlsx` | 27 / 39 | 右侧「管帽/吊绳」小表整块看不到 |
| `26MT-02N182-JX` | `-C_巨星_入库单_补款*.xlsx` | 25 | 第 25 列「做负重量」列看不到 |
| `25MT-05Q484-GYL` | `_供应链_入库单_(1).xlsx` | 25 | 同上 |

**修复**：`sheets_to_text()` 改为按「实际有内容的列」渲染（`used_width()`，顺带解决
openpyxl 把带格式的空列报成 16384 列的问题），上限提到 60 列 / 300 行，
真还有列没展示时在文本里明确写出「该表第 N~M 列未展示」。

**影响面**：全语料 2035 份表格附件里，列数 >24 的 53 份，其中走模型解析的 **6 份**；
行数 >200 的 0 份。这 6 份 + 1 份模型读错工作表 + 1 份批次标签重复的，共 **8 份已定向重跑**。

### 8.2 复核方法（当时的临时脚本 `tmp/qa_llm_parses.py`，已随清场规则删除）

对 124 份模型解析的附件做两道检查：

* **A 内部自洽**：`settled_totals.amount` 是否等于各 `settled_blocks` 之和；
* **B 原表逐格核对**：不信任模型，直接读源文件单元格，按「订单数据」标记行定位各
  「实发…」区块的列区间，把该区间「金额」列里**真实出现过的每个数**收集起来，
  模型给的每个区块金额必须能在对应区块里找到同一个数。

为什么用「逐格出现」而不是自己算合计：各厂合计行写法五花八门——有的合计含吊绳/管帽
（`26MT-03P200Y-HX`：A 区 = 明细 874,836.707 + 吊绳 360 + 管帽 274 = 875,470.707），
有的把合计写在备注行的金额列里（`25MT-03T650Y-HX` 的 78,811.68），
有的区块标签写重复了（`26MT-03T046Y` 两个「实发数据-A」），自己算反而更容易错。
（第一版复核脚本正是踩了这两个坑，报出 46/76 个假警报，已作废。）

**结果**：`settled_blocks` 的 **123/123 个区块金额全部在原表逐格找到**（其中 10 份因为是
结算清单式版式，只能做「金额必须出现在本表某金额列」的弱核对）；无对不上的附件。
另外，读取时统一把 `settled_totals.amount` 校正为区块之和（`normalize_settled()`），
避免模型两处数字打架。

### 8.6 选择层又修了三处（2026-09-24，第十四轮）

三处都是「钱本该算进来、结果被剔成 0」，都从**采购单级闭合**
（入库单实发总额 vs 飞书该单全部行合计）倒查出来：

### 8.5 仍然要留意的三处（已带证据，不影响已核对的总数）

1. `26MT-01P242Y-HD` 的 `-b_D` 文件里，模型把「a(C) 187,019.84 + b(D) 599,538.63」
   合成一个区块 786,558.47。**总额正确**（该单整单已发货），但 C/D 两批的分批金额丢了，
   分批成本只能按占比分摊。原始数值都在（`settled_totals` 里也写着 599,538.63），需要时可再拆。
2. `26MT-03T046Y` 的表把两个实发区块都标成「实发数据-A」，系统按「同批次标签金额冲突」
   拒绝直取、走分摊；该单元与飞书**分文不差**（24,086.40）。
3. `26MT-03P200Y-HX` 的 C 区：合计行 1,975,156.05，但 C 列逐行求和 2,216,921.11
   （其中 3 行 C 数量为 0/-6 却仍带金额，疑似整行金额被粘进 C 列）。该单两个单元与飞书
   差 0.01% / 0.07%，取的是合计行，属「单据自身前后不一致」，建议财务确认这一批。
