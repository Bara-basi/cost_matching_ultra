# 拆单：用「子集和（0-1 背包）」把出运产品行分配到报关单

## 要解决的问题

一张出运单对应多张报关单时，数据里没有「哪条产品属于哪张报关单」的直接线索，
只能**猜**。做法：把报关单的**报关金额**当背包容量，把出运产品行的**出运金额**当物品，
找一组正好装满的组合。

## 容量口径（实测确认）

```
报关单容量 = 该报关单各行报关金额之和 − 分到的运费
运费按「报关单张数」平分（strategy = equal）
```

依据：

- 26MT-07T042 海运费 2000，2 张报关单；扣掉各 1000 后两张报关单**精确闭合**；
- 全量运行里，155 张「只有运费」的出运单中，成功闭合的都用 `equal`；
  在「有运费且各策略结果不同」的强区分度案例里，`equal` 命中 7/8。

费用取自睿贝出运单的**客户费用信息**（`expenseList`），
目前只处理「运费」；含检验费等其它费用的出运单暂不纳入策略推断。

## 算法

`app/services/knapsack_split.py`

1. **精确子集和**：meet-in-the-middle（商品行 ≤36 时 2^18 规模，很快），
   允许 ±0.5 元容差吸收报关金额与 ERP 金额的舍入差；
2. **大池子兜底**：商品行很多时改用「按元粒度」的容量受限 DP（状态上限 40 万）；
3. **部分数量兜底**：仍无解时，按某条产品行的**外销单价 × 部分出运数量**配平，
   剩余金额再用整行精确凑齐（即你说的"拆解一条记录"）；
4. **报关单内部落到报关行**：按 供应商简称 → 海关编码 → 报关品名 依次匹配；
5. **费用分摊自适配**：`equal / by_weight / by_amount / none` 四种策略都跑一遍，
   取「精确闭合的报关单最多」的那种，并把结果记进台账。

启发式：候选行先按 **同海关编码 → 同供应商** 排序再求解，能显著收窄搜索范围。

## 费用口径：逐种费用猜测 + 台账统计

出运单的费用不只有运费，因此在容量计算上按**费用种类**分别处理：

1. **没有附加费用**（费用表为空）：容量 = 报关金额，直接对出运单做子集和；
2. **有附加费用**：对每种费用都枚举 4 种分摊口径
   （`equal` 按报关单张数平分 / `by_weight` 按报关重量 / `by_amount` 按报关金额 / `none` 不扣减），
   组合后取「精确闭合的报关单最多」的那组；
3. 每条记录把**每种费用最终命中的口径**写进台账
   `.cache/erp/reports/fee_strategy.xlsx`；
4. 推断时只统计**有区分度**的样本（报关单张数 > 1，且不同口径结果不同）——
   单张报关单时四种口径本就无法区分，不能当证据。

当前推断结果（样本还少，随数据积累会更稳）：

| 费用 | 命中分布 | 结论 |
| --- | --- | --- |
| 检验费 | by_weight=2 | 一致 → 按报关重量分摊 |
| 运费 | equal=2、none=1 | 倾向按报关单张数平分，样本不足 |
| 手续费 / 试样费 | none=1 | 不参与报关金额扣减 |

无附加费用的出运单 197 张；单张报关单（口径无法区分）138 张。

## 多解即报错（避免"猜错还当成功"）

拆单本质是猜，因此加了两道唯一性校验，任一不通过就**报错而不是判成功**：

1. **同价可替代**：走「部分数量匹配」时，若背包内某条记录在背包外存在
   **出运金额一致**的记录（互换后仍是同一组金额），判定解不唯一；
2. **口径不唯一**：若**另一种费用分摊口径**也能得到同样精确的解
   （指派结果不同），判定候选不唯一。

实测拦下 13 条「费用口径不唯一」+ 3 条「同价可替代」。

### 补充：子集和本身多解（2026-09-22 案例 26MT-03R236）

26MT-03R236 有三张报关单（管件 1488.68 / 法兰 5884.96 / 无缝管 1521.18），
出运单无附加费用，算法直接对整池做子集和。管件那张容量 1488.68，
**存在两组不同的记录都能凑出 1488.68**：

- 正解：鸿迪的 13 条管件行（5.18+26.40+4.43+9.24+16.00+136.09+14.13+17.04+172.80+1001.95+24.10+8.76+52.56）
- 误解：1 条鸿迪 + 5 条勇恒（5.18+650.85+65.73+292.16+292.16+182.60）

MITM 先命中哪一组取决于枚举顺序，于是两张报关单都混进了勇恒和鸿迪，
而飞书的正确答案是「223320260001182330→鸿迪、223320260001182341→勇恒」。

因此新增 `subset_sum_alternative_exists`：找到解后，逐个去掉解内元素再求解，
若仍能凑出同额 → 判**多解**并报错。全量因此新增 39 条「候选不唯一（子集和多解）」，
相应地从"一致"里退出。

> 可选的进一步优化：多解时优先取「供应商种类最少」的那组（本例正解只有鸿迪 1 家，
> 误解有 2 家），能把"报错"变成"择一"。尚未启用，待更多样本验证。

## 分层背包（先验：一张报关单通常对应整厂货物）

先验：不同工厂的交期与所在地不同，所以一张报关单通常对应**某个工厂的全部货物**，
或**若干工厂的全部货物**；例外才是同一工厂的货物分批报关。

据此把求解改成**由粗到细**三层：

| 层级 | 物品粒度 | 说明 |
| --- | --- | --- |
| L1 | 按供应商打包 | 一个工厂的本次全部出运行合并成一条大记录 |
| L2 | 按供应商+产品类型打包 | 工厂 + 产品类型合并 |
| L3 | 逐条产品行 | 现有细粒度（含部分数量兜底） |

规则：某层若**全部报关单都精确闭合且无多解**，直接采纳并退出；否则退到下一层。
组合记录不允许再按数量拆解。

实测（26MT-03R236 就是典型案例）：

| 指标 | 分层前 | 分层后 |
| --- | --- | --- |
| 拆出记录 | 248 | **288** |
| 比对单元 | 229 | **263** |
| 一致 | 214 | **244** |
| 异常 | 283 | **212** |

命中粒度分布：**按供应商打包 180**、按供应商+产品类型打包 3、逐条产品行 60
—— 印证了"一张报关单对应整厂货物"这个先验。
「候选不唯一（子集和多解）」从 39 条降到 21 条（粗粒度天然消除了大部分等价解）。

## 已修：三单互查直取 + 2025 回补 + 费用方向 + 部分数量分摊（2026-09-22）

你点名的三条 `25MT-06H655R1` / `25MT-07F591` / `26MT-03P039Y-B` 全部拆通，
根因不是一个而是五处，逐条修掉：

### 1. 产品行池子混进别的出运单（主因）

原 `collect_lines()` 把「按合同号直接取到的出运单产品行」和「整张订单下所有出运单
的产品行」**混在一起**喂给子集和：同一订单还有 A/C/D 张出运单时，池子里会多出
属于别张报关单的行，容量必然对不上（表现为「子集和无解」或「候选不唯一」）。

现在改成两级：**先用三单互查直取**——合同号 → 出运单列表的原生
`orderCode`/`invoiceCode`/`purchaseCode` → 该出运单明细，只拿它自己的产品行；
**只有窄集解不出来**，才放宽到整张订单的全部出运产品行兜底。

### 2. 出运明细可以按需联网补抓

`ensure_shipment_detail(invoice, online=ONLINE_TOPKUP=True)`：本地
`.cache/erp/details/shipments/` 没有该出运单时，直接用睿贝 MCP `shipment.find`
临时抓一次并落盘。跨年、漏抓的单子不必先跑一遍全量。

### 3. 2025 年出运明细已回补

`scripts/mcp_fetch_shipments.py --year 2025`：740 张全部抓完（首次 724 + 重试 6），
产品行 9,700+。`25MT-06H655R1`（R1 后缀的特殊单）、`25MT-07F591` 因此可查。
缓存重建后出运产品行索引 6,425 → **15,749**，出运单 620 → **1,175**。

### 4. 费用方向：报关金额「含」还是「不含」这笔费用

费用口径改成 `方向:方式`：

- `sub:equal` 报关金额已含该费用，按张数平分后**扣减**（原逻辑）；
- `add:equal` 出运金额 = 报关金额 + 该费用，按张数平分后**加回**。

`add` 只在常规口径解不齐时启用，且一次只把一笔费用设成 add，避免口径组合爆炸。
典型：`25MT-06H655R1` 客户费用里有一笔 `2400` 的**客户赔货金额**，
报关金额 2047.65 + 2400 = 出运金额 4447.65（口径记为 `(未命名):add:equal`）。

### 5. 部分数量分摊：一条产品行可以喂两张报关单

原来部分数量配平成功后会把**整行**从池子里拿走，导致同一产品行的剩余数量
无法再分给下一张报关单。现在按数量扣减、按比例折算剩余金额后留在池子里。

`26MT-03P039Y-B` 就是标准病例（飞书结果：无缝管→巨星、焊管→沪新）：

| 报关单 | 品名 | 报关金额 | 算法 |
| --- | --- | --- | --- |
| 222920260002074254 | 不锈钢焊管 | 82,509.84 | 焊管 327.42 × **252** = 82,509.84 |
| 222920260002074264 | 不锈钢焊管 | 180,735.84 | 剩余 **552** 条 = 327.42 × 552 |
| 222920260002074248 | 不锈钢无缝管 | 68,981.70 | 608.64 + 3,958.62 + 228.42 × **282** |
| 222920260002066284 | 不锈钢无缝管 | 189,239.16 | 127,565.76 + 228.42 × **270**（270+282=552 用完） |

### 6. 顺手修掉的两个小坑

- **去重 marker 未做数值归一**：`10` 与 `10.000000` 会当成两条行，导致每条产品行被算两遍（窄集 1 条变 2 条）；
- **供应商名称缺失**：MCP 明细的 `供应商名称` 常为空，用采购订单号回查采购列表的原生
  `supplierName`（否则「按供应商打包」会把所有缺名行挤进同一个筐）。

### 7. 性能

同一轮要跑「口径组合 × 报关单 × 粒度」上百次求解，直接跑 10 分钟以上跑不完。
几处优化后全量 **23 秒**：

- 半集枚举按候选行缓存（同一批行会被反复求解）；
- 单条金额 > 「容量 + 容差」的行先剪掉；
- 多解校验改成「一次 meet-in-the-middle 同时拿两组不同解」，不再是「逐条剔除重解 × 14 次」；
- 分摊额完全相同的口径组合不重复求解。

## 第二批修复：联合合同定位 + 费用残差 + 行内落行（2026-09-22）

### 1. 合同号 → 出运单：先整串匹配，匹配不上再按「订单核心」最小覆盖

`app/services/contract_shipments.py`（新增），接入 `shipment_invoices_for_contract`。

合同号是**出运单号的联合写法**（最小重复原则），一张报关单可以对应多张出运单：

| 合同号 | 实际出运单 |
| --- | --- |
| `26MT-06H124&08C122` | `26MT-06H124`、`26MT-08C122` |
| `26MT-01T050D&ADD1&080B&ADD1-B` | `PI-26MT-01T050D`、`PI-26MT-01T050ADD1&080B&080ADD1-B` |
| `26MT-06H278&08C282` | `26MT-06H278&08C282`、`S260814001` |

- 覆盖关系用睿贝原生 `orderCode` / `purchaseCode` 归一出「订单核心」
  （年份+MT+部门+业务员+三位流水[Y][-ADDn]，批次/工厂尾缀丢弃）；
- `invoiceCode` 只当「整串命中」的键——同一张出运单被拆成两张记录时，
  旧记录的发票名可能还挂着别人的订单号（`26MT-06H278&08C282` 实际只有 06H278 的行，
  08C282 已另立 `S260814001`）；
- 取「**最少张数**的出运单覆盖合同订单集合」的解；多解或覆盖不全就退回旧的基号模糊匹配，
  不硬猜。

另外：睿贝 MCP 偶发返回空单据（如 25MT-03P601Y 有单号无产品行），
此时退回 `shipment_lines.jsonl` 索引取该出运单的产品行。

### 2. 费用残差层：不再预先猜客户费用分摊口径

`knapsack_split.solve_residual`。当四种固定费用口径都凑不出精确解时启用：

- 以「供应商（工厂）」为单位整组分配产品行；
- 容量 = 报关金额（**不预先扣费用**），每张报关单分到的产品金额 ≤ 它的报关金额；
- 所有组都要用到，取残差平方和最小的解，残差即「落在该报关单上的客户费用」。

25MT-07F521Y 是典型案例：

```
报关金额合计 318220.31 = 产品行 299384.00 + 客户费用 18836.31（检验费 + 运费）
...926 → 榕圣 29097.24 + 萧星 1603.74 + 丰恒 23271.70 = 53972.68（精确闭合）
...278 → 勇恒 42360.94（精确闭合）
...069 → 鸿迪 77255.52（残差 3836.31）
...586 → 卓业 125672.70 + 希蒙 122.16（残差 15000.00）
残差合计 18836.31 = 客户费用总额 → 在约束下解唯一
```

### 3. 行内落行：同一家工厂的产品行整组落在同一报关行

`assign_to_rows` 改为：

1. 按**供应商**把产品行分组，整组与报关行的报关金额对号入座
   （品名/海关编码相符优先，其次要求金额几乎完全吻合）；
2. 整组放不下时才拆开，按金额贴合度逐条分摊给仍空着的报关行；
3. 老的「供应商→海关编码→品名→金额最近」口径与「空行从别的行借货」作为兜底，
   且任何报关行分不到产品行时都会进异常表，不再静默丢弃。

## 第三批：出运单号 ↔ 外销单号 映射表（2026-09-22）

### 1. 问题

一张出运单可以合并多个外销单，而报关单又按外销单拆开，例如：

```
出运单 26MT-10E185B&228A = 67579.40
  ├ 外销单 PI-26MT-10E185  ↔ 报关合同 26MT-10E185B    14019.00（不锈钢焊管，鼎上）
  ├ 外销单 PI-26MT-10E228  ↔ 报关合同 26MT-10E228A   19317.40（钢铁制软管，溪流）
  └ 两张外销单的无缝管行    ↔ 报关合同 26MT-10E185B&228A 34243.00
```

以前对联合合同号用「猜拆分位置」的办法，容易把出运单和报关单对错。

### 2. 映射表（`app/services/contract_shipments.py`）

对睿贝出运单列表里**每张出运单的 invoiceCode** 做一次最小重复拆分：

- 键 = **拆分结果**（字面拆分、保留批次尾缀，如 `26MT-10E185B + 26MT-10E228A`）；
- 值 = **原值**（`26MT-10E185B&228A`）。

建表结果：**1199 条，0 个键冲突**（用字面拆分后 `26MT-03R360A/B/C` 各占一个键，
不会像「订单核心」那样互相覆盖）。表已导出：
`.cache/erp/reports/contract_split_map.csv`（拆分结果 | 原值 | 段数）。

### 3. 报关合同号解析

`resolve_by_split_map`：

1. **整段命中**：合同号的拆分结果与某张出运单完全一致 → 直接取那张出运单；
2. **被包含命中**：合同号只是某张联合出运单的一段（上例的 26MT-10E185B / 26MT-10E228A）
   → 取**最小的**包含它的出运单，多张同样小则判多解不猜。

字面拆分在这里很关键：`26MT-10E228A` 不会被 `26MT-10E228B&281A&285A&348A` 抢走
（后者的字面段是 `26MT-10E228B/281A/285A/348A`）。

369 条报关合同里，**336 条**能由映射表直接解析；剩下的（如 `26MT-06H124&08C122`、
`26MT-01T050D&ADD1&080B&ADD1-B`）仍走「订单核心最小覆盖 + 基号兜底」。

两种解析结果**并列作为候选池**，谁能把该合同的报关单拆得更全就用谁
（评分：全部精确闭合 > 无多解 > 精确闭合张数 > 有落货的报关单数）。

这一层是兜底：只在金额法完全无解、且不存在多解时启用。

## 第四批：极小客户费用 = 精确信号（2026-09-22）

业务补充：报关金额与出运金额核算口径有细微差异时，业务员会**手工补一笔极小的客户费用**

据此 `scripts/run_split_knapsack.py` 增加规则：

- 取到该出运单的客户费用后，只要存在 `0 < 金额 ≤ 1` 的极小费用，就把背包**容差置 0**，
  只认定**完全一致**的解；
- 否则维持原来的 ±0.5 元容差。

- `26MT-01P242Y-C`：出运单里有 0.01 的补差，产品行 155268.17 + 0.01 = 报关金额 155268.18；

- `26MT-03P200Y-A&201Y-A`：9751 元级的小额报关单也不再被容差放进来。

## 第七批：`费用口径不唯一` 的成因与真凶（2026-09-22）

### 报错含义

`费用口径不唯一：试样费:add:by_amount、手续费:sub:by_amount、…` 里那一串是**试过的费用假设清单**，
格式 `费用名:方向:口径`：

- 方向 `sub` = 这笔费用已含在报关金额里，算容量时**扣掉**；`add` = 在报关金额之外，**加回去**；
- 口径 `equal/by_weight/by_amount/none` = 按报关单张数 / 按报关重量 / 按报关金额 / 不参与分摊；
- `@报关单号` 后缀（本批新增）= 只在这个**子集**里分摊。

判定方式：每种假设都完整解一遍 → 取「精确闭合的报关单最多」的那一档 → 若这一档里存在
**两组拆法不同**的解，就判「口径不唯一」，该合同所有报关单都不出结果（报异常而不是猜）。
所以它不是"算不出来"，而是"算得出来、但不止一种算法"。

### 真凶：同一产品行被存了两份

例：25MT-05Q442&ADD1（报关金额 32699.96 + 33641.66；出运单 66341.62 = 产品 64641.62 + 检验费 1700）。
真相是 1700 全落在无缝管那张单（32699.96 = 30999.96 + 1700）。但系统同时解出
`sub:none` 与 `sub:equal@{…564}` 两个 2/2 的解 → 判多解。

根因是这批产品行在库里存了两份：MCP 明细的 SKU 带换行（`1smls tube\n0.250.065`），
历史缓存里是空格（`1smls tube 0.250.065`），去重键不相等 → 每行翻倍。

- 后果①：`按供应商打包`/`按供应商+产品类型打包` 两个粗粒度层全部 0/2（金额翻倍，谁都凑不上）；
- 后果②：细粒度层因为"多出一份同样的行"而凭空多出第二组等价解 → 假多解。

修复：`run_split_knapsack.marker_key` 与 `shipment_index._normalise` 都把**内部空白**压成单空格
（换行/多空格等价），并重建 `shipment_line.jsonl` 索引（15749 → 15738 行）。

### 结果

## 第八批：把客户费用的「加减方向」定下来（2026-09-22）

### 结论一：`加减` 字段 MCP 取不到，但方向可以从 ERP 自己的数里解出来

- 睿贝 `客户费用信息` 的 `加减` 是 plus(+)/less(-) 单选；但 MCP `shipment.find` 返回的
  该字段**恒为空串**（353 条缓存 + 线上 12 张单据实测，含罚金/折扣/试样费）。
- 金额里也没有符号：全量 607 条费用行只有 **5 条负数**，全部在 `purchaseExpenseList`
  （`法兰赔款 -3862.37`、`06N078赔款抵扣 -160.00`、`03T206Y合同赔款 -1053.41`），
  **客户费用（expenseList）金额一律为正**。
- 但 ERP 自身成立一个恒等式：

```
出运总金额 − 产品行合计 = Σ(方向 × 客户费用)
```

实测 1182 张出运明细：895 张无客户费用；有费用的 287 张里 **271 张能唯一解出方向组合**
（15 张因两笔费用金额相同而多解、1 张因半包含订单等口径对不上）。例：

| 合同 | 费用 | 产品合计 → 出运总金额 | 差额 | 方向 |
| --- | --- | --- | --- | --- |
| 25MT-06H593 | 罚金 11804.81 | 591877.33 → 580072.52 | −11804.81 | less（本项目 `add`） |
| 26MT-03T202 | 检验费 1800 | 72434.33 → 74234.33 | +1800 | plus（本项目 `sub`） |
| 26MT-03P200Y-D | 木箱费 12500 + FOB退费 4050 | 469900.62 → 478350.62 | +8450 | 木箱费 plus / FOB退费 less |

### 结论二：方向已按 ERP 口径定死

`app/services/freight.py::fee_directions()`：逐张出运单用上面的恒等式解方向，
唯一解才采用；解不出来退回经验表 `FEE_DIRECTION_DEFAULTS`
（检验费/手续费/木箱费/试样费/模具费/内陆运费/仓储费/包装费 → sub；罚金/FOB退费/折扣 → add，
由 227 个全闭合合同统计得出）；最后才放开两个方向都试。

覆盖：63 个有费用的合同里，**54 个由恒等式定死方向**（检验费 sub×14、罚金 add×4、
运费 sub×16/add×2、折扣 add×2/sub×2 等）。

效果：一致 321、异常 57（与上一批相同）。方向维度被彻底消掉（组合数减半、结果可解释），
但异常没减少——因为剩下的 `费用口径不唯一` 都是**同一方向内的口径之争**
（按报关单张数 / 按重量 / 按金额 / 只摊给某个子集），不是加减方向之争。

### 补充：方向判定不再依赖费用名称（避免命名不规范导致误判）

- 方向**只认 ERP 恒等式**解出的唯一解；原「按费用名称的经验表」已取消用于定方向
  （保留在 `freight.py` 仅作背景说明）。费用名是空的、或写成 `税费`/`调尾差`/`三方检验费`/
  `小数点调节` 这类非规范名字，都不影响方向判定。
- 恒等式解不出来时（278 张有费用的出运单里有 16 张）**不猜**：两个方向都枚举，
  能唯一闭合才出结果，出现两种拆法就报多解。
- 风险量化：231 张单笔费用；35 张两笔（其中 13 张真正有加有减）、10 张三笔、各 1 张四笔/五笔。
  **262/278（94%）由恒等式唯一定死方向**，13 张混合加减的全部定死
  （如 25MT-01Q322 运费 +2500 / 折扣 −340.67；25MT-05Q062 五笔费用、两笔未命名，同样解出）。
  我们数据里真正的混合加减案例 26MT-03P200Y-D（木箱费 +12500、FOB退费 −4050）已拆对。
- 唯一遗留边角：**同一张单里同名费用一正一负**（全量仅 2 例，且费用名都是空的）——
  下游按费用名聚合无法区分正负，此时放弃该名字的方向、退回两方向枚举。

### 大池子 DP 的两个漏解 + 一格两个订单（2026-09-23）

**1）按「元」取整会把真解漏掉（真 bug）。** 大池子（候选 > `MAX_ITEMS`）用位图 DP 时
把每条记录都 `round(金额/100)` 成「元」，而窗口只按 `±容差` 取，于是**每行最多漂移 0.5 元**
的取整误差累计起来能把真解挤出窗口。实测 66 条记录整包正好等于容量，取整后合计却漂移
1.99 元，掉在 ±0.5 元窗口外 → 判「DP 未找到解」。

修法：粒度由细到粗自动选（分 → 十元 → 元 …），窗口按**行数**放宽
（`slack = 粒度 × (行数/2 + 2)`），候选总和解按「分」精确校验。金额不大时直接按「分」做，
彻底没有取整误差。效果：`26MT-06M008` 的 `310120260517117149`（66 行整包 = 容量）一次命中。

**2）「整包少装」这一类解 DP 看不到。** `310120260517117474` 容量 136890.17，
候选池三家工厂合计 136903.27，真相是**整包少装 2 支**：卓业有一行 4336.10 = 662 支 × 6.55，
只装 660 支 = 4323.00，正好差 13.10。DP 只认「整行」组合，永远看不到这种解；
而按供应商分组也解不出来（这一张报关单横跨三家工厂）。

修法：大池子分支在 DP 失败后先试「**整包 + 只有一条按数量少装**」（枚举哪一条少装、少装多少，
O(n) 枚举 + O(n) 校验），命中唯一才采纳；再不行才退回「按供应商分组」。
少装必须**按分精确闭合**——容差 0.5 元、单位价才一两元时容差内会冒出十几个假解
（实测卓业那条有 12 组假解），所以精确解优先，精确解不唯一就直接放弃。

**3）一格两个订单、两个公司要拆行（索引 + 取数两条路径）。** 出运产品行偶尔把多个采购订单
塞进一格：`采购订单号 = 26MT-03T046Y,26MT-03T046Y-XMLS`、`供应商 = 甲,乙`。
这时一行货来自两家工厂，不拆开整行只能算一家。

`shipment_index.split_merged_parts()` 负责拆：

- 只在**能确认是两家不同公司**时拆（供应商编码全部能解析出名称，且归一后的公司名不止一个）；
  解析不出、或只是同一家的两个账号（「麦金老账号 / 迈拓新账号」）时保持原样；
- 美元金额按**采购数量**分摊（采购数量之和正好等于该行出运数量，是 ERP 自己的口径），
  余数给最后一份保证合计不变；人民币金额用各采购单自己的 `productAmount`（两家单价不同，不能按数量摊）。

同一套逻辑也接在 `run_split_knapsack.collect_lines()` 上——那里直接读 MCP 出运明细，
不走索引，不接就会在比对时冒回合并行。

> 口径差异提醒：`26MT-03T046Y` 飞书按**重量**（579kg : 87kg）分摊报关金额，
> 我们按**数量**（403 : 60）。供应商与采购金额完全一致，但美元金额各差约 7 USD
> （6181.95 vs 6174.56、920.39 vs 927.78）。睿贝结构化字段里没有重量（净重只在入库单附件里），
> 所以这条差异是口径差异、不是错误。

### 可分数单位（米/千克）的小数配平（2026-09-23）

新增分数配平，条件按用户口径设计得**极严**：

3. 其余候选不超过 12 条（候选一多，能凑出余量的组合就成群，唯一性无从谈起）；
4. **只在整数口径完全解不齐时才启用**（见下）；
