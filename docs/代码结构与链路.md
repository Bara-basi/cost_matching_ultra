# 代码结构与链路

本文档说明当前项目的代码链路：数据从哪来、经过哪些模块、结果落到哪里、
以及新界面应该对接哪些接口。业务口径见 `docs/拆单说明.md`、
`docs/产品类型与报关重量口径.md`、`docs/当前状态与异常台账.md`。

> 当前状态：Vue 前端（`web/`，构建到 `web/dist`）已接入 `/api/*`，后端 FastAPI 服务在 `app/`。

---

## 一、总体数据流

```
                    ┌── 报关单 PDF（界面上传 / data/raw/customs_declaration）
                    │
输入来源 ───────────┼── 飞书多维表格（一键同步：按范围读取记录）
                    │
                    └── 手工粘贴（逐单核验）

            ↓ ① 解析           ↓ （飞书/手工输入本身已是结构化行，跳过解析）
      app/services/parser/     app/services/pipeline.py::write_declarations()
            ↓ 统一成同一张「报关单解析结果」表（列名一致）
            ↓ ② 拆单（子集和 / 背包）
      scripts/run_split_knapsack.py::run()  →  app/services/knapsack_split.py
        依据：合同号 → 出运单 → 按「采购订单 / 供应商 / 产品类型」拆记录
            ↓ ③ 成本匹配
      app/services/cost_match.py    用「入库单实发金额」定成本，按 RMB 货值摊
            ↓ ④ 整理成财务看得懂的行
      app/services/review.py        每条：异常类型 + 一句异常明细 + 睿贝/飞书入口
            ↓ ⑤ 任务编排与接口
      app/services/workspace.py  →  app/main.py（/api/*）
```

## 二、三条入口在代码里的走向

| 入口 | 接口 | 代码路径 |
| --- | --- | --- |
| 逐单核验 | `POST /api/lookup/parse` → `POST /api/lookup` | `app/services/lookup.py` 识别粘贴文本 → `pipeline.write_declarations()` 写成解析表 → 同一条拆单链路 |
| 文件匹配 | `POST /api/jobs`（上传 PDF/ZIP/Excel） | `pipeline.parse_pdfs()`（走 `app/services/parser/`）→ 拆单 → 成本匹配 |
| 一键同步 | `POST /api/sync/scan` → `GET .../plan` → `POST .../push` | `app/services/feishu_workflow.py` 读飞书范围 → 同样的拆单 + 成本匹配 → 写回飞书 |

三条入口最终都汇到同一处：

```
workspace.start_job()  →  后台线程跑 pipeline  →  结果落 .runtime/jobs/<任务号>/
```

每次操作都是**重新计算**，不复用历史结果。

## 四、睿贝数据侧（拆单的地基）

```
启动时 app/services/erp_sync.py::start_scheduler()   # 启动按需跑一次 + 每 12 小时一轮
        ↓ 后台子进程（不阻塞页面）
scripts/erp_sync.py
   ① 三类单据列表   ← ERP 直连（Playwright 重放内部接口），按主键合并（只增不丢）
   ② 出运明细       ← MCP shipment.find；缺的必抓，缓存超过 7 天重抓
   ③ 采购附件       ← MCP 抓附件清单并下载「入库单」（成本匹配唯一凭证，已下载跳过）
   ④ 入库单解析     ← 可选 `--with-grn-parse`，把新入库单解析成结构化金额
   ⑤ 重建索引       ← shipment_index.build()
```

**调度参数**（环境变量，`app/services/erp_sync.py`）：

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `ERP_SYNC_ENABLED` | `1` | 是否启用定时同步 |
| `ERP_SYNC_INTERVAL_HOURS` | `12` | 多久跑一轮（调度线程每 10 分钟检查一次） |
| `ERP_SYNC_REFRESH_DAYS` | `7` | 出运明细缓存超过多少天重抓 |
| `ERP_SYNC_ATTACHMENTS` | `1` | 同步时是否补抓采购附件/入库单 |

`GET /api/erp/sync` 会返回 `enabled / intervalHours / refreshDays / withAttachments /
running / ageHours / nextDueAt`，可据此判断下一轮何时跑；`POST /api/erp/sync` 可手工触发。
命令行等价入口：`scripts/erp_sync.py`（`--no-attachments` 跳过附件、`--lists-only` 只刷列表、
`--with-grn-parse` 顺带解析新入库单）。

落盘位置：

| 路径 | 内容 |
| --- | --- |
| `.cache/erp/shipments/shipments.jsonl` | 出运单列表 |
| `.cache/erp/purchases/purchases.jsonl` | 采购订单列表 |
| `.cache/erp/sale_orders/orders.jsonl` | 外销订单列表 |
| `.cache/erp/details/shipments/*.json` | 单张出运单明细（productList / expenseList） |
| `.cache/erp/index/shipment_lines.jsonl` | 出运产品行统一索引（拆单直接消费） |
| `.cache/erp/details/products/*.json` | 商品资料（产品编码 → 类别名称） |
| `.cache/erp/attachments/` | 采购附件与解析后的入库单 |
| `.cache/erp/sync_state.json` | 上次同步的状态与统计 |

## 六、结果字段与界面约定

`GET /api/jobs/{id}/rows` 返回（由 `app/services/review.py` 产出）：

```
报关单号、合同号_1、合同号（应收表格）、外销订单号、产品类型、报关品名、
供应商简称、供应商名称、采购订单号、报关金额、采购金额、报关重量、
异常类型、异常明细、出运金额合计、出运采购金额合计、分摊依据、
_睿贝采购单、_睿贝出运单、_飞书链接
```

界面上要处理的两种约定：

1. **范围内没有数据不算错误**：`POST /api/sync/scan` 返回
   `{"id": null, "selection": {...}, "message": "这段时间内没有可处理的数据（读取了 N 条记录）。"}`，
   弹提示即可，不要当异常处理。
2. **逐单核验不再拒核**（2026-09-29 用户判定：能算出正确金额 → 规则多余，去掉）：
   遇到「该出运单报关单不全 **且** 客户费用对不上」时，任务照常计算，
   由「睿贝出运明细兜底」把缺的报关行补出来（见下文），只把该条记录标成
   `异常类型=出运单有额外费用`、`异常明细` 写明还差多少。

判定口径（详见 `docs/当前状态与异常台账.md`）：

- 只有「金额算漏」才算异常；同一采购组内分摊位置不同不算异常。
- 与飞书核对：采购金额相同即正常；只有组内分配不同记「正常，但额外金额分配不一致」；
  报关金额、采购金额允许行级不同，合计一致即正常。

### 「缺报关单」按**本批**口径判定（2026-09-29 修正）

`app/services/review.py` 判「缺报关单」时，比的是**本批出运单上该采购单应有的货值**
（`_batch_purchase_totals`，按本条记录的 `合同号_1` 取出运明细聚合），
**不再**拿该采购单在所有批次上的累计货值去比。

原因：同一张采购单常分 A/B/C 多批出运，用累计值比会把**每一批**都误判成"还有报关单没拿到"。
实测全量 462 条拆单记录：旧口径误报 55 条，新口径只报 5 条（均为真实缺口）。
出运明细取不到时不报（宁可少报，不误报）。

### 飞书区间的「同合同补齐」不再依赖日期

`app/services/feishu_workflow.py::select_records` 原先只在**填了日期范围**时才把
「同合同其它商品行」补进计算池；只按报关单号 / 合同号筛选时会漏，导致拆单池不完整、
成本算不出来。现在只要本批选中行能解析出合同号就补齐。

### 「本批报关单齐不齐」以 ERP `出运总金额` 为基准（2026-09-29 用户确认）

`pipeline.scan_receivable()`（逐单核验的拒核判据）改为：

```
本批同一出运单的 报关金额合计  ==  睿贝出运单的「出运总金额」   （差额 ≤ 5，见下文容差 ±5）
```

`出运总金额` 已经叠加全部客户费用，是 ERP 给出的最终参考金额。实例 26MT-06H192B：
产品出运金额 159,144.80 − 罚金 4,086.83 = **出运总金额 155,057.97** = 报关金额。

判据含义：不等 → 本批报关单不齐；若该出运单还带客户费用（罚金 / 运费 / 检验费…），
说明金额分配规则依赖缺失的那几张报关单 → 逐单核验拒绝并提示补齐。
取不到 `出运总金额` 时退回「产品金额 + 客户费用」的旧算法。

注意：`review.py` 判「缺报关单」用的是**产品货值口径**（本批出运单上该采购单应有的 RMB 货值），
与费用无关，因此罚金 / 运费不会影响它。

### 金额容差 ±5（2026-09-29 用户口径）

一张报关单的金额基本不可能低于 50，所以「出运总金额 vs 报关金额合计」「本批货值覆盖」
两处的容差由 ±1 放宽到 **±5 本币**（`pipeline.scan_receivable` / `review.EQUAL`）。
实例：25MT-07F379Y-F&477G 出运总金额 66,496.03、报关金额 66,495（差 1.03），此前误判「缺报关单」。

### 联合合同号不能在 `&` 处截断（2026-09-29 修复）

粘贴解析的正则原来停在 `&`：`25MT-07F379Y-F&477G` 被解析成 `25MT-07F379Y-F`，
导致后续按**批次记号**取入库单区块时取错（F 区块 125,697.30，而正确是 G 区块 283,281.40），
成本少了约 2.3 万。现在：

1. 解析正则整段吃掉 `&` 连接的联合号；
2. 「单字母结尾」判为批次（出运合同），「2~5 位字母后缀」才判为采购单（-ZY/-YH/-GYL）；
3. 补全时若飞书的合同号比我方更完整（我方值是其子集），以飞书为准。

### 睿贝深链接（2026-09-29 修复）

详情页的睿贝按钮原先只是列表页链接，点不到具体单据。现在 `review.erp_links()` 用本地缓存里的
ERP 数字 ID 生成深链接（拿不到 ID 才退回列表页）：

```
采购单 https://erp.mtholdinggroup.com/purchase_toUpdate?openWindow=Y&type=view&id=<purchase_id>&openhash=costReview
出运单 https://erp.mtholdinggroup.com/shipment_toUpdate?openWindow=Y&type=view&id=<shipmentId>&openhash=costReview
```

联合合同号（`25MT-07F379Y-F&477G`）按 `&` 拆段逐个查索引后取到 shipmentId。
字段 `_睿贝采购单链接` / `_睿贝出运单链接` 随 `/api/jobs/{id}/rows` 一起返回。

### 写回开关（2026-09-29）

`WORKBENCH_WRITE_TOKEN` **不是飞书 token**，而是工作台自己的一道远端写回口令：
工作台对外暴露时，远端请求必须带上它才能写回飞书。现在本机（127.0.0.1 / ::1）访问默认放行——
`/api/health` 会返回 `writeEnabled=true`、`local=true`，界面上的「确认写回」可直接使用；
只有局域网 / 公网访问才需要配置该变量。

### 不要求「必须有报关单 PDF」：睿贝出运明细兜底（2026-09-29 用户口径）

**原则**：部分记录是财务照着报关单手填的，报关单 PDF 本来就可能没有；任何「必须有报关单才能算」
的逻辑都是错的。成本核算只依赖睿贝出运明细 + 已有报关行。

实现（`pipeline.run_round`，工作台三个入口统一走它）：

1. 先正常跑一轮拆单；
2. 读 `拆单_未认领产品行.xlsx`，把**没有任何报关单认领**的产品行按「合同号 + 采购单」合并，
   生成**补充报关行**（金额 = 这些行的出运金额合计，报关单号留空，来源写「睿贝出运明细补充」）；
3. 用该出运单的 ERP 「出运总金额」比对差额（客户费用等），按金额占比摊到补充行上；
4. 把补充行追加到解析结果表，**再跑一轮拆单**。

结果行的 `异常类型` 仍是「正常」，但 `异常明细` 会写明
「本行金额来自睿贝出运明细（该批报关单未到齐）」；界面详情页会以黄色提示条展示。
同时**取消**了逐单核验原来「报关单不全 + 有客户费用 → 拒核」的硬拦截。

实例 26MT-07T118：出运单 9 个采购单、飞书只有 6 行（财务手填），原来 9 行全红且 3 个采购单算不出成本；
现在 14 条记录全部正常、9 个采购单的成本都算出来了，补充的 3 个采购单
（26MT-07T135 / 125-HD / 125）在 `异常明细` 里标注了来源。

> 遗留：当多行报关行共用同一个报关单号、同一品名且没有商品序号时（手填的典型形态），
> 拆单只能按金额硬凑，**行级 `报关金额` 会分配不准**（采购金额不受影响）。
> 需要时可以加一条「按采购单金额整组对号入座」的前置匹配来改善。

### 财务手工补回的「拆单结果」先合并回报关行（2026-09-29 用户口径）

**背景**：一张报关单 PDF 本来对应一行、一行一个报关单号。但财务为了查看，会把脚本跑出的
**拆单结果又补回多维表**，于是同一个报关单号下出现多行（一行一条拆分记录）。这类数据
不是我们的处理目标（已经拆完算完），但可能有"拆了没算"的脏数据，必须能接住。

**做法**（`pipeline.write_declarations` → `merge_declaration_rows`）：在把输入写成
「解析结果」表之前，把 **同一 `报关单号 + 合同号_1 + 报关品名`** 的多行合并成一条，
报关金额与报关重量相加、商品序号清空，然后当成**一条报关行**交给拆单。

- 只作用于飞书 / 手工 / 模板输入；我们自己解析的 PDF 结果不经过这里，
  所以"真的多商品报关"（不同品名）不会被误并；
- 合并后金额、重量是加总回来的，随后的拆单、成本匹配**一律以系统核算结果为准**。

实例 26MT-07T118（报关单 310120260517830361 有 6 行手填记录，各对应一个采购单）：

| 合并前（财务手填 6 行） | 合并后 |
| --- | --- |
| 419.63 / 5,888.25 / 11,151.45 / 21,885.82 / 21,707.60 / 5,390.42 | 合计 66,443.17 的一条报关行 |

重算后 6 条记录各自对上自己的采购单（报关金额与那 6 行完全一致，采购金额取各自入库单区块），
另外 3 个没有报关单的采购单由「睿贝出运明细」补出成本，11 条记录全部正常。

### 粘贴补全提速（2026-09-29）

`lookup._fetch()` 改为：按**报关单号 / 合同号各一次**飞书端检索（OR 条件分批，最多 20 个/次），
两类检索并行，并加 5 分钟短期缓存。实测 3 个报关单：首次 10.4 秒（原来 2 个要 21 秒），
同批重复补全 0 秒。

### 逐单核验粘贴补全：同一报关单的多行拆完单记录并回一条（2026-09-29）

**问题**：粘贴一行（比如只给报关单号 / 合同号）后，`lookup.enrich_rows()` 会从飞书把该单的
商品行**全部展开**。对财务手工补回表里的脏数据来说，展开出来的多行其实是**同一张报关单的拆单结果**，
于是界面上出现一张报关单七八行，后续还会重复计算金额。

**做法**（`app/services/lookup.py`，与飞书区间、`pipeline.merge_declaration_rows` 同一口径）：

1. `_collapse_records()` 先把飞书候选行按 **`报关单号 + 合同号_1 + 报关品名`** 分组，
   同组多行**报关金额、报关重量相加**、清空商品序号后并成一条，再交给下面的匹配 / 展开；
   报关单号为空的记录不并（避免把不同报关单的行并到一起）。
2. 粘贴的是「拆散的那一行」时也认得出来：金额比对会同时匹配合并后的合计和它的成员金额，
   命中后按**合并合计**回填，并在 `_补全说明` 里写明「同报关单 N 行拆分记录已并回一条」。
3. 一次粘贴同一报关单的多行拆完单记录时，`enrich_rows()` 收尾再按同一把键去重，
   只留合并后的那一条（否则下游再相加会把同一批金额算两遍）。

不同品名的多商品报关不受影响：比如 224420260000612240（镍合金法兰 2 行 + 镍合金管件 1 行）
合并后仍是 2 条，法兰 4,580.48 / 管件 1,514.58。

### 报关合同号写了批次、睿贝却没有这批出运单 → 报异常，不再拿别的批次顶替（2026-09-29）

**实例**：出运单 26MT-03R036F、报关单 224420260014225760（56 美元 / 14 千克 / 不锈钢管件）。
财务在飞书区间核验时得到采购金额 325.27，但睿贝里根本没有 26MT-03R036F 这张出运单——
该订单只有 **A–E 五批**（A/B 鸿迪、A/C 勇恒、D/E 巨星，最后一批 2026-05-20）；
这条报关行本身是「漏发补发」（飞书备注：成本在之前已经开完），9 月才出口，批次字母才排到 F。

**原因**：合同号定位不到时，代码会走两层兜底
（`shipment_invoices_for_contract` 的**基号兜底** + `run_split_knapsack` 的**订单全量兜底**），
把同订单 A–E 五批共 279 条产品行全拉进候选池；56 美元的报关行被凑到批次 A 的 4 条产品行上
（合计 56.00 美元 / 324.45 元），采购金额再按该采购单入库单实发占比摊出 **325.27 元**；
紧接着「睿贝出运明细兜底」又拿同一堆池子凭空补出 3 条补充报关行（采购金额 136 万 / 35.6 万 / 1 万）。

**改法**（2026-09-29 用户口径：本地能确定的异常就要报出来）：

1. `shipment_detail.names_batch()`：判断合同号是否**点明了批次**
   （核心之外的字母，`26MT-03R036F` → 批次 F；`26MT-03R302` 没写批次）。
2. `shipment_invoices_for_contract()` 的基号兜底加上守卫：点了批次却定位不到同名出运单时，
   不再返回「同订单其它批次」；没写批次的合同（`26MT-03R302`、`26MT-08C020`）照旧按基号取全部批次。
3. `run_split_knapsack` 在合同级先拦一道：**点了批次 + 定位不到出运单 + 「按报关金额认领出运单」也没命中**
   → 直接写 `拆单_本地异常`（说明：`睿贝里没有这张出运单（26MT-03R036F），该订单只有 A/B/C/D/E 批`），
   不再走「订单全量兜底」。保留金额认领是为了不误伤「飞书批次字母写错、但金额能唯一对上出运单」的场景。

**顺带补的洞**：`拆单_本地异常.xlsx` 以前不进结果，财务在界面上看不到这些记录
（选中的未核算行会凭空少一条）。现在 `review._local_exception_rows()` 把它们补成正常结果行，
只给一个异常类型和一句财务话：

| 拆单引擎的说明 | 结果里的异常类型 | 结果里的异常明细 |
| --- | --- | --- |
| 无出运产品行 / 睿贝里没有这张出运单 | 找不到出运单 | 睿贝里没有这张出运单（…），该订单只有 A/B/C/D/E 批 |
| 子集和无精确解 | 拆单失败 | 报关金额与睿贝出运金额凑不出精确对应，请核对这一单的报关单与出运单。 |
| 子集和多解 | 拆单失败 | 有不止一种拆法都能凑出同额，需要人工确认。 |
| 费用口径不唯一 | 拆单失败 | 这一单的费用有多种分摊口径都能对上，需要人工确认。 |
| ERP 数据异常（反推失败） | 拆单失败 | 睿贝里这家供应商不生产这个产品，采购单号也对不上，需要人工确认。 |

**影响面**：拿 PDF 解析结果（369 条报关商品行）全量对比，新旧结果**完全一致**（0 行差异）；
飞书副本里受影响的只有 8 个合同，其中仅 26MT-03R036F 有 1 条未核算行。

### 「按报关金额认领出运单」只认同一订单家族（2026-09-29 修复，逐条核验同样受影响）

**实例**：26MT-03P315B / 报关单 310120260515144783 的核算结果里出现一条「正常」行，
采购单却是毫不相关的 **25MT-03T614-HD**、采购金额 ¥751.20。

**原因**：`collect_by_declared_amount()`（「一张报关单 ↔ 一张出运单，金额相等」）原来在
**全库**出运单里找金额相等的单：这条报关行金额 400 美元，而 25MT-03T614 的出运总金额恰好也是
400 美元（它是别的订单的零星补料），于是整张 T614 的池子被拉进来、被当成这一单的货拆了出去，
采购金额取该采购单的入库单实发 751.20。同一批里另一条行（鸿迪不生产该产品）也是被这个错误的
池子带出来的 ERP 数据矛盾提示。

**改法**：新增 `order_family()`——订单核心去掉**年份前缀**与 **-ADDn 尾缀**后比较
（`25MT/26MT` 混写、`-ADD1-A` vs `-B`、出运单没写 ADD 这些真实写法仍算同一家族，
`26MT-03P315` 与 `25MT-03T614` 不再算同一家族）；认领范围只在这个家族内，
跨订单的金额巧合不再认单。

**影响面**：PDF 解析结果全量跑一遍，只有 1 行变化——26MT-05Q171B / 224420260013129505
（你 2026-09-23 已核实的「睿贝没有这批出运单，零星样品」案例）不再被瞎认到
26MT-02N126Y-HD（原来显示采购金额 193,887.00），现在它只留在 `拆单结果_已核实.xlsx`。

### 逐条核验粘贴：一行里有「合同号」和「合同号_1」时取更具体的那一个（2026-09-29）

**实例**：同一条 26MT-03R036F / 224420260014225760，飞书区间算对了，逐条核验却仍按正常算
（采购金额 325.27）——因为从飞书整行复制出来的文本里同时带着 `26MT-03R036`（合同号）与
`26MT-03R036F`（合同号_1），旧解析取了**先出现的基号**，等于退回到「没写批次」的老口径。

**改法**（`app/services/lookup.py`）：

1. `_extract_row()`：同一行有多个候选合同时，丢掉「是另一个候选的前缀」的那个
   （`26MT-03R036` < `26MT-03R036F`、`25MT-07F477` < `25MT-07F477&26MT-07C330`）；
   采购单号带工厂后缀（`-HD`）时基号仍然当合同号，不受影响；
2. `_merge()`：补全时「我方值是飞书值的前缀」也算飞书更完整，用飞书的值覆盖。
